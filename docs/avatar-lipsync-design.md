# 头像直播（音频驱动口型）设计方案

> **说明**：本功能是 ppobs 的原创新增。随 `feature/audioshift` 分支上的头像直播需求创建，
> 在编码开始前编写，兼作实现期间的参照和后续 PR 说明，结构沿用
> `docs/virtual-background-design.md` 与 `docs/audioshift-design.md` 的既有体例。
>
> **第 3 节是本文档要先回答的问题**：这个功能该做成滤镜还是插件。

## 1. 目标

为 ppobs 增加"头像直播"能力：主播选定一个头像（真人头像照片，或动物／卡通头像），
直播时该头像出现在画面**右下角、最上层图层**，并**根据主播的声音实时开口说话**（口型
与语音同步）。

目标使用方式：

```text
麦克风源 --(AudioShift 变声等滤镜)--> OBS 混音 ----------------> 推流 / 录制
     |                                                              ^
     +--(取后置滤镜音频)--> 头像源 --(生成口型画面)--> 场景右下角 ---+
```

全部推理在本机完成，不调用云端数字人服务，不上传语音或人像数据。

## 2. 范围与非目标

### 2.1 第一版（P0）范围

- Windows x64
- 一个独立的 OBS **源**（输入源）类型，可加入任意场景、可自由摆放与缩放
- 头像资源：单张图片，或 2~10 秒的 idle 循环视频（轻微眨眼／点头）
- 两种口型驱动模式（见第 5 节）：
  - **模式 A 真人头像**：MuseTalk 潜空间重绘，口型质量高，需要独立显卡
  - **模式 B 动物／卡通头像**：音频驱动口型贴图，CPU 即可，无模型依赖
- 从指定音频源取**后置滤镜**音频（即变声之后、实际播出的那一路）
- 延迟测量 + 音视频对齐（见第 7.3 节）
- 中英文配置界面
- 任何一环失败（无显卡／sidecar 崩溃／推理超时）自动降级，**不得黑屏、不得卡住预览、
  不得崩溃 OBS**

### 2.2 第一版不包含（P1 / P2 展望）

- 头像的头部姿态／表情驱动（只做口型，不做点头、转头、眨眼的音频驱动）
- 全身数字人、手势
- 文本驱动（TTS → 口型）；P0 只驱动真实麦克风音频
- 情绪识别驱动表情
- 多头像同时在线（P0 允许多个源实例，但只保证一个走模式 A）
- macOS / Linux
- 头像的自动摆放向导（P0 手工摆放，P1 在 frontend 加一键添加）

## 3. 关键结论：做成插件里的「源」，不是滤镜

OBS 里"滤镜"和"插件"不是同一层概念——**滤镜本身就住在插件里**。所以真正要定的是：
这个功能应该注册成 OBS 的哪种对象。结论是**新建一个插件模块 `plugins/obs-avatar`，
在其中注册一个输入源（`OBS_SOURCE_TYPE_INPUT`）**，而不是注册成滤镜。

理由：

1. **它是发生器，不是变换器。** 滤镜的语义是"拿父源的画面／音频，改一改再交出去"。
   头像画面不来自任何父源，它是凭音频从零生成的新画面。做成视频滤镜就必须找一个
   无关的视频源当宿主，纯属寄生。
2. **"右下角、最上层"本来就是场景项（scene item）的能力。** 源进场景自带位置、缩放、
   图层顺序、裁剪、过渡。做成滤镜画出来的头像会被父源的变换和裁剪连带影响：父源一缩放
   头像跟着变形，父源一隐藏头像跟着消失，父源分辨率一变锚点就跑。
3. **音频滤镜根本无法输出视频。** 挂在麦克风上的滤镜 `output_flags` 只有
   `OBS_SOURCE_AUDIO`，滤镜链里没有给音频滤镜交付画面的通路。想用音频滤镜实现，就只能
   让它写一块全局状态再由另一个源去读——那本质上就是方案一，只是多了一层隐式耦合。
4. **隔离性。** 模式 A 要加载 3.4GB 的 UNet 和 CUDA/DirectML 运行时。
   `obs-filters.dll` 现在已经承载了虚拟背景（ONNX Runtime）和 AudioShift（SoundTouch），
   都是已在用的功能；把一个会 OOM、会占满显存、会被驱动拖死的推理栈塞进同一个模块，
   一次崩溃就带走抠像和变声。独立模块（P0）+ 独立进程（见第 6 节）是必要的。
5. **`plugins/obs-filters` 的体量。** 该目录已有 30+ 源文件，再加一套头像资源管理、
   sidecar 协议、口型合成，审阅与同步上游都会更难。

唯一会让人想选滤镜的场景是"头像必须跟着某个具体源一起被整体处理"（比如和摄像头画面
一起被同一套抠像／调色处理）。本需求不是这样：头像是独立的一层叠加物。

**取音频不需要滤镜。** 已有现成做法：`obs_source_add_audio_capture_callback()` 按名字
挂到目标音频源上拿音频，`plugins/obs-filters/compressor-filter.c:403` 的 sidechain 就是
这么做的。关键是这个回调在 `source_output_audio_data()` 里触发，位于
`filter_async_audio()` **之后**（`libobs/obs-source.c:4051`），所以拿到的是**后置滤镜
音频**——正是经过 AudioShift 变声、实际要播出去的那一路。对口型必须对播出音频，这一点
刚好天然成立。

### 3.1 对象清单

| 对象 | 类型 | 作用 |
|---|---|---|
| `ppobs_avatar_source` | `OBS_SOURCE_TYPE_INPUT`，`OBS_SOURCE_VIDEO \| OBS_SOURCE_CUSTOM_DRAW \| OBS_SOURCE_SRGB` | 头像画面的唯一出口；属性界面；取音频；延迟对齐 |
| （P1）frontend 动作 | `obs_frontend` 菜单项 | 一键创建源并吸附到右下角、置顶 |

头像源**不输出音频**（不设 `OBS_SOURCE_AUDIO`）：音频已经由原麦克风源走混音链路播出，
头像源再出一路就会重复。

## 4. 推荐开源技术栈

### 4.1 推荐组合

| 环节 | 选择 | 许可证 | 说明 |
|---|---|---|---|
| 真人口型生成 | **MuseTalk**（TMElyralab） | 代码 MIT，官方声明权重可商用 | 潜空间重绘，实时模式为"离线预处理 + 在线 UNet/VAE 解码" |
| 音频特征 | whisper-tiny encoder | MIT | MuseTalk 的既定输入 |
| 图像编解码 | ft-mse-VAE | 需核验（见 4.3） | MuseTalk 的既定组件 |
| 动物／卡通口型 | **自研 viseme 口型贴图** | 本仓库代码 | 无模型、无显卡依赖，兼作降级路径 |
| 推理运行时 | P0 sidecar 内的 PyTorch/TensorRT；P1 进程内 ONNX Runtime | — | 见第 6 节 |

### 4.2 为什么选 MuseTalk

- **实时架构是现成的**：人脸检测、人脸解析、VAE 编码全部在"头像准备"阶段一次性做完并
  缓存（`coords.pkl` / `latents.pt` / mask / full_imgs），直播时只跑
  whisper → UNet → VAE decode → 融合回原图。这正好对应"先选头像，再开播"的交互。
- **许可证干净**：代码 MIT，官方明确不限制商用——对商业直播产品是硬条件。
- **只需要音频**：不需要摄像头拍主播的脸，不需要驱动视频。
- 对照过的替代品：Wav2Lip（分辨率低、嘴部模糊，且权重为非商用）、SadTalker／EchoMimic
  （生成整头，非实时）、商业数字人 SDK（要联网、要授权费、人像数据外发）。

### 4.3 许可证核验要求（并入发行包前的阻断项）

按 `docs/virtual-background-design.md` §3.6 的规则逐条留痕，不得凭上游 README 一句
"可商用"就放行。必须单独核验并记录：

- MuseTalk 代码仓库 LICENSE（已查：MIT）
- MuseTalk 发布权重的实际授权条款
- **UNet 源自 Stable Diffusion v1.4**——需要确认 CreativeML OpenRAIL-M 的衍生约束是否
  随权重传递
- `sd-vae-ft-mse` 的模型卡授权
- whisper-tiny 权重授权（MIT）
- MuseTalk 预处理所用的**人脸检测／人脸解析权重**——这一项风险最高，部分 mmpose/dwpose
  系权重为非商用；若踩中，需替换为可商用的检测器，或把预处理限制在不随产品分发的
  "头像准备"工具里

核验结论回写本节，未核验完不进 release 分支。

## 5. 两种口型驱动模式

需求同时要求"真人头像"和"动物头像"。这两者不能用同一套模型，必须明确分开——这是本方案
最重要的一个设计取舍。

### 5.1 模式 A：真人头像（MuseTalk）

- 适用：正脸或接近正脸的真人照片／短视频
- 质量：口型自然、牙齿和口腔内部有合理纹理，是目前开源方案里可商用的最好一档
- 代价：需要独立显卡；需要头像准备阶段；端到端延迟高（第 7.3 节）

### 5.2 模式 B：动物／卡通头像（张嘴变形，原计划为口型贴图）

**MuseTalk 对动物头像不可用**，这不是调参能解决的：它的预处理强制要求人脸检测与人脸
解析，真实动物头像（猫、狗）基本检测不到人脸；偶尔检测到，解析出的"嘴部区域"会被重绘成
人嘴，结果不可用。拟人化卡通角色视情况可能部分可用，但不可作为承诺。

所以动物与卡通头像走一条完全不同的、确定可行的路径：

1. 头像资源包里带一组**口型图**：闭口 + A / E / I / O / U（可选补 M-B-P、F-V），
   即 Preston Blair 那套 6~10 型，以及嘴部贴合锚点
2. 音频按 20ms 分帧 → 能量门限判定"有没有在说话" → 轻量 viseme 判定（P0 用能量 +
   谱质心的启发式控制张合度，P1 换 MFCC + 小型分类器区分元音）
3. 口型权重在相邻两型之间做时间平滑，按锚点合成到头像底图上
4. 叠加 idle 动画（眨眼、轻微上下浮动），避免"死图动嘴"

- 代价：CPU 占用可忽略（预计 <1ms/帧），延迟仅缓冲长度（~30~60ms），无模型、无显卡、
  无许可证问题
- **同时是模式 A 的降级路径**：显卡不可用、sidecar 未安装、推理超时或崩溃时，自动落到
  模式 B，画面继续动，不黑屏

### 5.3 单张图片的局限

单张静态图片只能做到"头不动、嘴在动"，观感僵硬。两种模式都建议支持 2~10 秒 idle 循环
素材（MuseTalk 的实时模式本身就是按帧序列循环驱动的，天然支持）。属性界面里要把这点
说清楚，而不是让用户自己发现。

## 6. 进程模型：P0 用 sidecar，接口留给进程内推理

### 6.1 为什么 P0 不做进程内推理

- 现有 `.deps/onnxruntime-1.23.2` 是 **CPU 版** NuGet 包。MuseTalk 的 UNet 是 SD v1.4
  量级（`unet.pth` 3.4GB），CPU 上没有任何实时可能——虚拟背景那边 256px 的 MODNet 多线程
  优化后也要 24.5ms/帧，量级差了几十倍。
- MuseTalk 官方没有提供 ONNX 导出。自行导出 whisper encoder + UNet + VAE decoder 三件套
  是一项独立的、结果不确定的工程（算子兼容、精度对齐、显存布局），不应该挡在"功能能不能
  跑起来"前面。
- 推理栈崩溃／显存耗尽不能带走 OBS 进程。直播场景下 OBS 崩溃的代价是断流。

### 6.2 sidecar 形态

```text
obs64.exe
  └─ obs-avatar.dll
       ├─ avatar-engine-viseme   (进程内, CPU, 模式 B)
       └─ avatar-engine-sidecar  (客户端)
              │  命名管道 (双向, 长度前缀消息)
              v
       ppobs-avatar-worker        (独立进程, 持有 MuseTalk + CUDA/TensorRT)
```

- **控制与数据同管道**：`HELLO/READY`（协商头像包、分辨率、帧率）、`AUDIO`（16kHz 单声道
  float32 分块）、`FRAME`（BGRA + 该帧对应的音频时间戳）、`STAT`（实测推理耗时、丢帧数）、
  `LOG`（worker 的日志行转进 obs.log）、`ERROR`、`BYE`。256×256 BGRA @25fps 只有
  6.4MB/s，管道足够；共享内存（Windows file mapping）留作 P1 优化。

#### 6.2.1 线格式与方向（阶段 C 已落地）

权威定义在 `plugins/obs-avatar/avatar-sidecar-protocol.h`。几个在实现时定下来的点：

- **插件是管道的服务端，worker 是客户端。** 这个方向是刻意选的：从 Python 连一个命名管道
  就是 `open(r"\\.\pipe\name", "r+b")`，而*创建*一个则需要 pywin32。于是 worker 侧的传输
  层零第三方依赖，同时访问控制归 OS 管，而不是任何本机进程都能连的 localhost 端口。
- **字节流 + 自带长度分帧**，不用消息模式管道（`PIPE_TYPE_MESSAGE`）：消息模式在 Python
  的 `open()` 这一侧没有对应物。
- 消息头 8 字节：`uint32` 负载长度、`uint16` 类型、`uint16` 保留**必须为 0**。保留字段将来
  赋予含义时，老读端会直接拒收而不是误读。
- **类型字段不在分帧层校验**：更新的 worker 发来没见过的类型，正确反应是读掉负载并忽略，
  而不是拆掉一条本来好用的管道。只有长度和保留字段是读端必须据此行动的。
- 一切整数小端，逐字节读写，不 memcpy 结构体 —— 两端是不同语言不同编译器，结构体填充和
  主机字节序不能参与进来。Python 侧用 `struct.pack("<...")` 说同一套。
- 帧尺寸校验用 64 位算术：`width * height * 4` 在 uint32 能表达的范围内就会溢出，一个溢出
  后恰好等于 `payload_len` 的乘积会把远小于声明尺寸的缓冲交给调用方。
- **所有管道 I/O 用 overlapped**，不是为了吞吐（6.4MB/s 用不着），而是为了退出确定：阻塞
  I/O 下停在 `ConnectNamedPipe` 或 `ReadFile` 里的读线程只能靠取消别人的同步 I/O 来放行，
  那件事做错一点 OBS 就会在退出时挂住。现在每个等待都是 `{io 事件, 停止事件}` 的
  `WaitForMultipleObjects`，停止就是一次 `SetEvent`。
- 两端的字节级 fixture 是**同一组**：`avatar-protocol-test.c` 和 worker 的 `--selftest` 各
  自钉同样几串字节。两种语言对不上是这个协议最可能出的故障，所以它是唯一从两侧都测的东西。

#### 6.2.2 `CROP`：只传重绘的区域（协议版本 2）

`FRAME` 传整张画面，`CROP` 只传**被重绘的那块区域**，并且**把人脸解析的 mask 放在它的 alpha
通道里**，由插件在 GPU 上叠到它已经持有的素材纹理上。

动机是实测出来的，不是设计洁癖：worker 侧合成占了模式 A 每帧开销的一半以上（143 ms 里的
72 ms），而且没有一毫秒在 GPU 上。`paste(im, box, mask)` 本来就是以 mask 为 alpha 的合成，
所以把 mask 当 alpha 发过来、让 GPU 做最后一步，是**同一个运算**换个地方做。效果见 10.2：
贴回降到 15.1 ms/帧，帧负载从 3 MB 降到几百 KB。

**版本号为此从 1 升到 2，而不是依赖"未知类型跳过"那条前向兼容规则。** 一个默默忽略所有
`CROP` 的旧插件会显示一张静止头像——那看起来像 worker 停止产出，而不像版本不匹配。拒绝连接
才说得清问题所在。

校验上多了一条：区域必须**落在参考帧之内**。一个被轻信的 x/y 会把纹理放到素材外面，或者加上
宽度之后在 32 位里回绕、看起来刚好合适（`avatar-protocol-test.c` 钉了 `0xFFFFFFF0` 这个用例）。
READY 里的尺寸从此是**参考帧的坐标空间**而不是负载尺寸，所以上限从 1024 放宽到 8192——1080p
的头像是合理的参考帧，即使没有任何单条消息能装下它。
- **worker 的实现可替换**：P0 直接包装 MuseTalk 官方实时推理脚本（Python），最快拿到
  可用闭环；P1 换 TensorRT／C++ worker；P2 若 ONNX 导出成功，可做成进程内引擎而协议不变。
- **生命周期归插件管**：源启用时拉起 worker，源禁用／删除时结束；worker 异常退出按退避
  重拉（上限 3 次），期间走模式 B；永不让 OBS 的图形线程等 worker。
- **worker 不随 OBS 编译**：放 `tools/musetalk-sidecar/`，由安装包或单独的"头像能力"
  可选组件分发。插件检测不到 worker 时，属性界面只给模式 B 并写明原因（沿用虚拟背景
  "未配置模型时直通并留日志"的做法）。

## 7. 实时管线

### 7.1 线程职责

| 线程 | 职责 | 禁止 |
|---|---|---|
| OBS 音频线程（回调） | 取后置滤镜音频 → 48kHz 多声道 → 16kHz 单声道 → 写环形缓冲 | 禁止任何推理、禁止阻塞锁 |
| 头像工作线程 | 从环形缓冲取音频块 → 送引擎 → 取回帧 → `obs_source_output_video2()` | 禁止触碰图形上下文 |
| OBS 图形线程 | 只做已就绪帧的渲染 | 禁止等待工作线程 |

线程模型照抄 `background-segmentation-filter.c` 的既有形状（`pthread_mutex` +
`os_event_t` 唤醒 + 工作线程），差别是输入来自音频环形缓冲而不是视频帧。

### 7.1.1 渲染方式：同步自绘，不走异步源（阶段 A 的修订）

本节原本写的是 `OBS_SOURCE_ASYNC` + `obs_source_set_async_unbuffered(true)`，实现阶段 A
时改成了**同步自绘**（`OBS_SOURCE_CUSTOM_DRAW`），理由：

- 模式 B 的口型合成本质上是"底图 + 口型贴图按锚点叠加"，这是一个 GPU 合成任务。同步自绘
  可以直接在 `video_render` 里按层画；走异步源就得先在 CPU 上合出一张完整帧再交给 OBS，
  白搭一次全画面的 CPU 合成和一次上传。
- 动图素材（GIF/WebP）的 idle 循环由 `gs_image_file4_tick()` 免费提供，异步路径下得自己
  解码和定时。
- 异步源默认缓冲，关掉缓冲后的语义就是"显示最新到达的帧"——这与同步路径下"画当前最新
  纹理"完全一样，没有额外收益。
- 阶段 C 从 worker 收到的 BGRA 帧，用一张动态纹理 `gs_texture_set_image()` 上传即可，
  约二十行，不需要为此改变整条路径的形状。

代价是 `video_render` 里不能用 libobs 替我们开好的那个 technique pass（占位方块和头像
纹理用的 effect 不同），所以必须自己 `gs_effect_loop()`——这正是 `CUSTOM_DRAW` 的含义。

### 7.2 音频取样

- 目标音频源按**名字**保存在源设置里（与 compressor sidechain 一致），源重命名／不存在时
  走模式 B 的静默态，并在属性界面提示
- `struct audio_data` 是 OBS 混音采样率下的 float planar；下混为单声道后重采样到
  16kHz（whisper 的要求）
- 环形缓冲按"最新优先"丢弃：直播宁可丢旧音频也不要让口型越跑越慢

### 7.3 延迟与音视频对齐（本方案最容易翻车的一节）

模式 A 的在线路径需要当前帧**附近**的 whisper 特征窗口（含少量"未来"音频）+ UNet +
VAE 解码 + 融合，端到端预计 **150~400ms**。也就是说，当播出音频里说出"啊"的那一刻，
对应的头像画面还没生成出来。

对齐手段，按优先级：

1. **把播出音频整体延后，延后量 = 实测头像延迟。** 在 OBS 里就是被取音的那个音频源上的
   「同步偏移」：`obs_source_set_sync_offset()`（纳秒，正值延后音频）。插件实测稳定后
   提供"自动对齐"开关，由插件写入该偏移，并在界面上显示当前实测延迟。
2. **副作用必须说清楚**：延后音频会让场景里**所有**画面相对音频提前。如果场景里同时有
   真人摄像头出镜，真人的唇形会反过来对不上，此时需要给摄像头源加等量的「渲染延迟」
   滤镜。属性界面要就此给出提示。
3. **不对齐是不可接受的**：ITU-R BT.1359 对音视频不同步的容忍区间是音频滞后 90ms 以内、
   提前 185ms 以内，而观众对"数字人嘴型不对"的敏感度远高于一般画面。验收目标定
   **|偏差| ≤ 80ms**。

模式 B 的延迟只有缓冲长度（~30~60ms），在容忍区间内，默认不需要偏移。

### 7.3.1 模式 A 的延迟下限是结构性的（实现后的修订）

MuseTalk 的音频接口是**按片段**设计的，不是流式：`get_audio_feature()` 接受的是一个 wav
**文件路径**，`get_whisper_chunk()` 需要整段的 `librosa_length` 才能切出每帧对应的特征。所以
一条连续的麦克风流必须被切成窗口，每个窗口当成一个小片段跑一次。

**窗口时长因此是延迟的硬下限**，再加上这一窗的推理时间。默认 15 帧（25fps 下 0.6 秒）的窗口
意味着端到端远超半秒 —— 本节上面定的 80ms 验收目标对模式 A **不可能达到**。

这不是优化问题，是接口形状决定的：把窗口缩小只是用 GPU 的单次调用开销去换延迟，换不到精度。
所以模式 A 的口型对齐**只能靠把播出音频整体延后**来实现，也就是本节第 1 条的同步偏移 ——
那条从"锦上添花"变成了模式 A 能用的前提条件。

模式 B 不受这个限制（它逐 20ms 窗推进，无需未来音频），这也是它作为降级路径之外的另一个价值。

### 7.3.2 worker 必须跑在 MuseTalk 自己的 Python 环境里

MuseTalk 要 Python 3.10 + CUDA 11.8 + `mmcv==2.0.1`/`mmdet==3.1.0`/`mmpose==1.1.0`，和现代
环境（Python 3.13、numpy 2.x）冲突。本机已有可用的 venv：
`D:\github\MuseTalk\venv\Scripts\python.exe`（torch 2.0.1+cu118，CUDA 可用）。

所以 `musetalk_engine.py` 是**延迟导入**的：`--engine stub` 和 `--selftest` 在裸 Python 下照常
工作，只有模式 A 需要那套环境。这也是插件将来拉起 worker 时必须用绝对解释器路径、而不能指望
`python` 在 PATH 上的原因。

### 7.4 帧率与陈旧度

- 默认生成 25fps，可设 15/20/25/30，沿用虚拟背景"推理帧率"属性的做法
- 画面与音频的对应关系由 `FRAME` 消息里的音频时间戳维持；超过 2 帧未按时到达则保持上一帧
  （嘴不乱动），超过 500ms 未到达则切模式 B 并记一条日志

### 7.4.1 接到源上之后的几个决定（已落地）

**场景项的尺寸不跟着生成帧变。** 有头像素材时源的尺寸就是素材的尺寸，生成的帧缩放进这个
框里。反过来（报告生成帧的尺寸）会让 worker 一连上、一掉线，场景项就跳一次大小 —— 用户
刚摆好位置就看着它变形。一个稳定的框比跟生成器的像素网格对齐更值钱；而且真引擎最终是把
重绘结果融合回整张头像再送出来，两个尺寸本来就会一致。代价是 stub 的 256×256 放大到大图
会模糊，这是 stub 固有的，不是设计问题。

**只在时间戳变化时上传纹理。** `video_render` 每个输出都会调一次 —— 预览、节目、每个投影
窗口 —— 对同一批像素重复上传纯属浪费。

**引擎指针在锁内交换，在锁外销毁。** 销毁一个引擎要 join 它的读线程；为了一次属性编辑就让
图形线程等在那上面，是把界面卡顿变成丢帧的标准做法。

**陈旧帧回退：超过 500ms 没有新帧就不再显示生成帧**，回落到静态素材，并记一行日志；恢复
时再记一行。一张冻住的嘴留在直播画面上比一张静止的头像更糟 —— 它看起来还在说话。模式 B
落地后，这里就是口型贴图引擎接管的位置。

**日志里带上帧延迟。** 音频时间线和帧时间戳在同一个坐标系里，两者相减就是当前画面落后
声音多少毫秒 —— 阶段 D 要补偿的正是这个数，不需要比对任何时钟。

**音频没有路可走时不会堆积。** 口型驱动关闭时取到的音频照样被取空丢掉，环形缓冲不会一直
满着让丢弃计数失去意义。

## 8. 头像准备（离线，一次性）

模式 A 必须先做一次准备，产出可直接喂给在线路径的缓存：

```text
用户选图/短视频
  -> 人脸检测 + 对齐 + 裁剪
  -> 人脸解析得到嘴部重绘区域 mask
  -> 逐帧 VAE 编码 -> latents
  -> 写入头像包目录: full_imgs/ mask/ coords.pkl latents.pt meta.json
```

- 由 worker 侧完成（它已经持有模型），插件只负责发起、显示进度、校验产物
- `meta.json` 记录模型版本、尺寸、帧数、准备时所用的 worker 版本——模型升级后缓存要失效
- 准备失败（检测不到人脸、侧脸过多、分辨率过低）要给**可行动的**错误原因，而不是
  "处理失败"：这是用户选动物头像时最先撞上的提示，要在这里直接引导去模式 B

### 8.1 资源与权重目录（阶段 A 已落地）

权重和头像包都放在 OBS 配置目录下的 `background-models` 里 —— 与虚拟背景共用同一个目录，
本部署的既定选择：一台机器上的 AI 权重集中在一处，分发和排查都只有一个地方要看。各功能
用自己的子目录，不会撞文件名：

```text
便携:  <obs>/config/background-models            （如 build_x64/rundir/RelWithDebInfo/config/background-models）
安装:  %APPDATA%/background-models

  background-models/*.onnx          抠像模型（obs-filters 的）
  background-models/avatars/<id>/   已准备好的头像包（阶段 C）
```

> **修订：MuseTalk 权重不放这里。** 原计划是 `background-models/musetalk/`，实现时改掉了。
> MuseTalk 自己的模块按相对路径找权重（`FaceParsing` 直接去拿
> `./models/face-parse-bisent/...`），所以 worker 必须 `chdir` 到 MuseTalk 的 checkout 里才
> 能加载；把 6.8GB 权重复制进 OBS 的配置目录既没好处，又会让官方脚本失效。worker 改为接受
> `--musetalk-dir`（默认 `D:\github\MuseTalk`，也可用环境变量 `MUSETALK_DIR`）。
>
> 留在 `background-models/` 的只有**已准备好的头像包**——那部分是 OBS 侧要读的缓存，不是
> 第三方权重。
>
> 顺带印证了 §4.3 的判断：风险最高的 `dwpose` 和 `face-parse-bisent` 只在头像准备阶段用，
> 在线推流路径碰不到它们。准备工具不随产品分发，这两个的授权问题就绕开了。

解析逻辑在 `plugins/obs-avatar/avatar-assets.c`，与 `background-segmentation-filter.c`
同一套：取自 `obs_module_config_path()` 而不是 `os_get_config_path()`（后者在 Windows 上
被写死为 `%APPDATA%`，便携模式会伸进登录用户的漫游目录）；带不带 `obs-studio` 的两种读法
都搜。模块加载时会把解析出的路径打一行日志，属性界面也会显示它 —— 目录还不存在时也要显示
出来，否则用户无从下手。要把头像资源挪到独立目录，只需改 `AVATAR_ASSET_DIR` 一个常量。

同样是在撒谎。

## 10. 性能与硬件要求

- MuseTalk 官方给出的实时指标是 **NVIDIA Tesla V100 上 30fps+**；社区实践普遍把可实时
  的消费级门槛放在 **RTX 3090 及以上**。fp16 下最低显存约 4GB（`unet.pth` 3.4GB），
  实测 RTX 5090 约 8.5GB 占用。
- **OBS 本机同时还要编码和推流**，GPU 争用是真实风险，不能只看模型的孤立帧率。P0 的性能
  验收必须是"开播状态下"的联测：头像 25fps、编码不丢帧、预览不卡。
- 必须实测并记录（照 `matting-bench.c` 的做法写一个基准）：
  - whisper / UNet / VAE decode 各段耗时 ✅ 见 10.1
  - 不同生成帧率下的 GPU 占用与编码丢帧数（待测：目前都是 GPU 空闲时测的）
  - 模式 B 的 CPU 占用

### 10.1 实测：RTX 4060 Laptop（8GB），MuseTalk v1.5 fp16

单张静态头像（768×1024 输出），0.6 秒窗口，稳态（预热后），GPU 空闲：

| batch | UNet | VAE decode | 贴回(CPU) | 整体 | 峰值显存 |
|---:|---:|---:|---:|---:|---:|
| 1 | 37.7 ms | 33.2 ms | 66.6 ms | 159 ms/帧 | 6.68 GB |
| 2 | 21.8 ms | 36.6 ms | 66.6 ms | 145 ms/帧 | 6.91 GB |
| 4 | 14.4 ms | 37.3 ms | 71.9 ms | 145 ms/帧 | 6.91 GB |
| 8 | **11.3 ms** | 37.6 ms | 72.2 ms | **143 ms/帧** | 6.91 GB |

一次性成本：模型加载 + 头像准备 **54.8 秒**。whisper 特征摊薄后 **<1 ms/帧**（固定成本，窗口
越大越可忽略）。

**结论与原先的猜测相反：最大的一块不是模型，是 CPU 上的贴回。** 72 ms/帧里没有一毫秒在 GPU
上。而且进一步看 `get_image_blending` 的实现，**开销根本不在合成上**——真正的 paste 只发生在
`crop_box` 范围内，整帧的部分全是两次 768×1024 的 PIL 转换和两次通道翻转。

### 10.2 把贴回挪到 GPU 之后（CROP 消息）

`paste(im, box, mask)` 的语义就是以 mask 为 alpha 的合成，所以这件事 GPU 能原样接手。改法见
6.2.2：worker 只在 `crop_box` 内 paste、把 mask 当 alpha 通道随区域一起发，插件在 GPU 上叠到
它已经持有的素材纹理。同一台机器、同一组对比：

| batch | UNet | VAE decode | 区域合成 | 整体 | 对比改前 |
|---:|---:|---:|---:|---:|---:|
| 1 | 36.5 ms | 33.0 ms | 14.4 ms | 88 ms/帧 | 159 → 88 |
| 2 | 21.8 ms | 36.6 ms | 15.3 ms | 76 ms/帧 | 145 → 76 |
| 4 | 14.1 ms | 37.3 ms | 15.0 ms | 69 ms/帧 | 145 → 69 |
| 8 | **11.2 ms** | 37.7 ms | **15.1 ms** | **66 ms/帧** | 143 → 66 |

- 贴回 **72.2 → 15.1 ms/帧**（4.8 倍），整体 **143 → 66 ms/帧**（2.2 倍）
- 帧负载从约 3 MB 降到区域大小（典型 300×360 BGRA ≈ 430 KB）
- **15fps 现在是实时的**：66 ms/帧 ≈ 15.1fps，15 帧音频恰好 0.99 秒跑完
- 25fps（40 ms 预算）仍差 1.65 倍

**下一个杠杆明确了：VAE 解码的 37.7 ms 占了 57%。** UNet 已经只有 11.2 ms，区域合成 15.1 ms。

### 10.3 半高解码 + 参考帧限幅：40.7 ms/帧（24.6fps）

两处改动，都来自同一个观察——**不要为到不了屏幕的像素付钱**。

**一、VAE 只解码 mask 保留的那些 latent 行。** `get_image_prepare_material` 把 mask 在
crop_box 中线以上清零（`keep upper_boundary_ratio of talking area`），所以完整 256×256 的上半
张被乘零丢掉。只解码需要的行：

- 起始行**从 mask 量出来，不假设 0.5**。那条清零线是按 crop_box 的坐标算的，不是 face bbox
  的，两者只在扩展恰好居中时重合。实测起始行是 **11**（共 32 行），硬编码 0.5 会多切三行、
  正好砍进 mask 开始生效的区域
- 多解码 2 行 latent（16 像素）当上下文再丢掉：解码器是卷积的，部分解码的上边缘在感受野
  填满前是错的

**二、准备阶段把参考帧限到长边 1024。** 不是性能优化，是**修一个会让功能完全不工作的 bug**：
测试素材是 1944×2592 的手机照片，在那个尺寸上 crop_box 会超过协议单条消息的上限（边长 1024、
负载 4 MiB；1500×1800 的 BGRA 是 10 MiB），插件会逐条拒收，现象看起来像 worker 没在产出。
限幅放在准备阶段而不是事后降采样区域，是因为协议假设"负载的像素数就是它的目标矩形"。
不损失任何到得了屏幕的分辨率：模型无论如何只重绘 256×256，插件最终合成的是用户自己的全分辨率
素材。

| | UNet | VAE | 区域合成 | 整体 | fps |
|---|---:|---:|---:|---:|---:|
| 改前（worker 侧整帧贴回） | 11.3 | 37.6 | 72.2 | 143 ms | 7.0 |
| GPU 贴回（§10.2） | 11.2 | 37.7 | 15.1 | 66 ms | 15.3 |
| + 参考帧限幅 | 11.2 | 37.6 | ~5 | 53 ms | 18.8 |
| **+ 半高解码** | **11.2** | **24.6** | **~5** | **40.7 ms** | **24.6** |

**保真度**：在 mask 真正保留的像素上，与全解码的平均差异 **1.01/255**（不到一个最低有效位），
最坏单像素 15/255，位置在部分解码的上边缘、alpha 刚非零处，混合权重极低。

最大区域实测 **632×632**（在 768×1024 的参考帧里），1.6 MB，落在协议上限内。

**结论：单看推理，25fps 已经基本到手**（40.7 ms vs 40.0 ms 的预算，差 1.7%）。VAE 现在占
60%，仍是下一个杠杆——INT8 TensorRT 若把它降到 10ms 量级，就有余量去抵消 OBS 自身编码的争用。

仍未验证的仍然是那条：**以上全部 GPU 空闲时测得**，开播状态下的联测没做。

### 10.4 试过 400×400 的硬上限：实测没有带来提速，已改回自动限幅

曾经按"限制尺寸可以大幅降低处理复杂度"的判断，把模式 A 改成拒绝任何一边超过 400 像素的素材。
实测否定了这个判断，**最终改回自动限幅到 1024、不拒绝大素材**。留下这一节是因为数据本身有用。

同一套 A/B，素材换成 321×396：

同一轮里测的一对（避免跨轮的频率波动混进对比）：

| 素材 | 参考帧 | 全解码 | 半高解码 | 最大区域 | 保真度（均值/最坏） |
|---|---|---:|---:|---|---|
| greg01（1944×2592，限幅） | 768×1024 | 56.1 ms | **41.2 ms/帧** | 632×632 | 1.01 / 15 |
| greg02（原生） | 321×396 | 52.6 ms | **39.9 ms/帧** | 321×342 | 1.42 / 17 |

**小素材快了 1.3 ms，也就是没快。** 这与 10.1~10.3 的结论一致：模型永远在 256×256 上工作，
UNet + VAE 的 36 ms 与源图尺寸无关，尺寸只能影响区域合成那几毫秒。（同一组素材先前测出 45.2，
是运行间的频率波动；在 8GB 笔记本卡上这种量级的抖动必须靠重复测量才能分辨，不能凭单次下结论。）

保真度则略有下降（均值 1.01 → 1.42/255）：321×396 上人脸约 180×220，裁剪要被**放大**到
256×256 才进模型，模型拿到的真实细节比大图少。

**所以上限换来的只是确定性，不是速度**，而自动限幅到 1024 同样给出那份确定性——crop_box 实测
最大 632×632，离协议的 1024 边长和 4 MiB 负载都有余量。既然收益一样而代价（拒绝用户的照片、
逼每个人先过一遍图像编辑器）只在硬上限那一侧，就改回了自动限幅。要速度得去动 VAE（它现在占
55%），不是去动素材尺寸。

> **顺带发现的一个真 bug，只有小素材才会暴露。** `get_crop_box` 按人脸中心扩展 1.5 倍且
> **不裁剪到画面内**。MuseTalk 自己没事，因为它用 PIL 的 `.crop()`，越界会补边；而 §10.2 为
> 省掉整帧 PIL 转换换成了 numpy 切片，**负索引在 numpy 里是从尾部数起**，于是切出空区域、
> 后续 `cv2.resize` 断言失败。大素材上 crop_box 永远落在画面内，所以此前一直看不到。
>
> 修法必须三处一起：裁剪到画面内（空区域退回全透明）、**mask 取对应窗口而不是整体缩放**
> （mask 是按未裁剪的框生成的，直接 resize 会让混合区整体滑动、偏离嘴部）、上报裁剪后的矩形。
>
> 教训：**用 numpy 切片替换 PIL 的 crop 是一处有隐含语义差异的优化**，越界容忍这件事只在
> 素材变小后才会被发现。

**仍未验证**：以上全部是 GPU 空闲时测的。峰值显存 6.91/8 GB，实际开播时 OBS 自己的合成和编码
器要抢同一张卡，很可能顶出去。"开播状态下联测"这条验收不能省。

**显存是真实风险**：峰值 6.91 GB / 8 GB，而这是 OBS 没在编码的情况。实际开播时 OBS 自己的
合成和编码器要抢同一张卡，很可能顶出去——WDDM 不会报错，只会悄悄回落系统内存然后慢一个
数量级（我自己的测量就撞过这个，见下）。

> **测量陷阱留档**：第一轮测出 VAE 600 ms/帧、整体 21 倍于实时，是**我的测量脚本的错**——
> 它在同一进程里连续构造两个引擎，`del engine` 之后没有 `torch.cuda.empty_cache()`，第二个
> 引擎是在显存被前一个占着的情况下跑的，于是真的发生了 WDDM 回落。加上缓存清理和预热轮之后
> 才是上表的数。教训：在 8GB 卡上测这种模型，每轮之间必须清缓存并重置峰值统计，否则测的是
> 显存不足而不是算力。
- 跑不动时的明确行为：降帧率 → 降分辨率 → 切模式 B，每一步都写日志。

**改了原计划的一处：没有做口型贴图，改成在素材上做张嘴变形。**

原计划是一组 viseme 口型图（闭口 + A/E/I/O/U）按锚点贴合。它更好看，但有个前提：得有人把那
组图画出来。而"让我家狗说话"的用户手里只有一张照片，任何画好的嘴都对不上那张脸。

所以改成沿一条线把图拉开再填充开口内部——只需要这张图，加一个"嘴在哪"的矩形。拉开是对称的：
嘴线以下的内容往下移、以上的往上移，位移相同，所以是下巴张开而不是整个头变大。参与权重在椭圆
边缘渐隐，变形区和没变形的脸之间不会出现硬边。

代价要说清楚：**这做到的是"下巴跟着说话开合"，不是分辨元音的口型**。要分辨 A 和 O，要么有画好
的 viseme 图集，要么上分类器——两者都是这个基础之上的增量。能跟着语音开合，已经是"在说话"这个
观感的大头。

口型图集那条路没有废弃：素材里带口型图时它严格更好，属于后续增量。

**嘴部位置用鼠标拖，不靠滑块找。** 六个滑块能表达嘴在哪，但没人会靠拖数字找到一张嘴。源加上
`OBS_SOURCE_INTERACTION` 后就能在自己的坐标系里收到鼠标事件（右键源 →「交互」）：左键拖动设
嘴中心，滚轮缩放大小，结果写回源的设置，所以拖完能存盘、滑块也会跟着变。

配套加了一个「显示嘴部区域轮廓」（默认开）。这不是锦上添花：区域要是落在下巴上，画面看起来
像是功能坏了，而不是位置不对 —— 变形明明在发生，只是没发生在嘴上。有了绿色轮廓，这两件事
一眼就能分开。它会画进节目输出，所以开播前要关掉，属性里的文字也这么写了。

## 12. 测试要求

> **`assert()` 在本仓库的测试里是空操作。** RelWithDebInfo 定义了 `NDEBUG`，`assert()`
> 随之消失，于是测试程序照常运行、照常退出 0、什么也没验证 —— 看起来和通过一模一样
> （征兆通常是"只在 assert 里被读到的局部变量未被引用"这种警告）。本模块的测试改用
> `avatar-test-check.h` 里的 `CHECK`，那是一个真的分支。`plugins/obs-filters/` 下现有的
> 几个测试仍在用 `assert()`，同样受影响，但不在本功能的改动范围内。

### 自动化测试（照 `audioshift-filter-test.c` / `matting-models-test.c` 的形状）
- 张口映射与平滑：门限以下闭口、满量程不过冲、退化区间（灵敏度拖到底）不除零、开比合快、
  与音频窗长无关 ✅ `avatar-viseme-test`
- 音频重采样：48k/44.1k 多声道 → 16k 单声道，长度与相位正确
- 环形缓冲：溢出丢旧、读写并发无数据竞争 ✅ `avatar-audio-tap-test`
- sidecar 协议：分帧、负载校验、保留字段、未知类型前向兼容、尺寸溢出 ✅
  `avatar-protocol-test`（字节级 fixture 与 worker 的 `--selftest` 是同一组）
- 两端真实会话：握手、音频外发、帧回传、BYE 退出 ✅ `avatar-sidecar-loopback-test`
- 时间戳对齐：给定延迟，偏移计算正确（阶段 D）

**环回测试里真正值得写的那一条断言**：从"大声"音频窗生成的帧，和从静音窗生成的帧，必须
不同，而且必须差在嘴上（实测 3726 像素 vs 0 像素）。只断言"有帧回来"会在音频被完全忽略的
情况下照样通过 —— 那恰恰是这条链路最容易出的故障。

环回测试需要运行时有 Python。缺了解释器时它**显式 SKIP 并打印原因**（已实测），不是静默
跳过也不是失败：构建 OBS 的机器不一定装了 Python，但一个悄悄跳过的测试比没有测试更坏。

## 13. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 动物头像在模式 A 下不可用 | 需求的一半落空 | 模式 B 作为动物／卡通的正式路径，而不是临时补丁（第 5.2 节） |
| 延迟导致口型对不上 | 功能观感不可接受 | 自动同步偏移 + 验收门槛 80ms（第 7.3 节） |
| GPU 与编码争用 | 直播丢帧 | 开播状态下联测；降级阶梯（第 10 节） |
| 许可证踩中非商用权重 | 不能随产品分发 | 核验为阻断项，预处理模型可限制在不分发的准备工具里（第 4.3 节） |
| 单图头像观感僵硬 | 用户觉得"不像活人" | 支持 idle 循环素材并在界面上引导 |
| 3.4GB 模型的分发体积 | 安装包膨胀 | worker 与权重做成可选组件，不随主安装包 |
| MuseTalk 无官方 ONNX 导出 | 无法进程内推理 | P0 用 sidecar，接口留好；导出作为 P2 的独立工作项 |
