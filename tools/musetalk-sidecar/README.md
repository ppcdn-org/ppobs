# ppobs 头像口型 worker

模式 A（MuseTalk）的推理进程。不随 OBS 编译，也不进主安装包 —— 见
`docs/avatar-lipsync-design.md` 第 6 节：3.4GB 的 UNet 和 CUDA 运行时不能塞进 OBS 进程，
推理崩溃或显存耗尽不能把直播一起带走。

## 协议

`plugins/obs-avatar/avatar-sidecar-protocol.h` 是唯一权威。

**插件是管道的服务端，worker 是客户端。** 这是刻意的：从 Python 连一个命名管道就是
`open(r"\\.\pipe\name", "r+b")`，而*创建*一个则需要 pywin32。顺带还让访问控制归 OS 管，
而不是任何本机进程都能连的 localhost 端口。

字节序一律小端。每条消息是 8 字节头（uint32 负载长度、uint16 类型、uint16 保留必须为 0）
加负载。`--selftest` 里固定的那几串字节与 `avatar-protocol-test.c` 里的是同一组 —— 两种
语言对不上会在测试里炸，而不是在直播画面上变成一团花屏。

## 跑起来

**默认由插件自己拉起。** 把口型驱动选成「真人（MuseTalk worker）」，插件就会创建管道、
启动 worker、等它连上；worker 退出或崩溃后按 1s、2s、4s……（上限 30s）的间隔重新拉起，
连续稳定运行 10 秒以上才把间隔重置。worker 在一个 Windows job object 里，OBS 即使崩溃，
worker 也会被一并收掉，不会留一个占着显存的孤儿进程。

属性里有五项（只在 MuseTalk worker 模式下显示）：

| 属性 | 留空时 |
|---|---|
| 自动启动 worker | 默认勾选；取消则回到手动模式（见下） |
| 口型幅度 | 默认 200%，运行时生效（经 `MOUTH_GAIN` 消息发给 worker，不用重启） |
| MuseTalk 目录 | 默认 `D:\github\MuseTalk`，环境变量 `MUSETALK_DIR` 可改默认值 |
| Python 解释器 | 用 `<MuseTalk 目录>\venv\Scripts\python.exe`；没有 venv 才退到 PATH 里的 `python` |
| worker 脚本 | 用编译时记下的源码树里的 `ppobs_avatar_worker.py` |

**口型幅度**：MuseTalk v1.5 在不少脸上嘴只张一点点，模型里没有对应的旋钮，把音频放大也没用（Whisper
特征做了归一化）。worker 启动时先算一遍静音下 UNet 的输出作为"嘴的静止形状"，之后每一帧输出
`静止 + 幅度 × (输出 - 静止)`，在隐空间里放大偏移。实测（`greg02.jpg`）100%、150% 几乎看不出张嘴，
200% 清楚，300% 开口更大但嘴角出现发白的伪影，所以默认 200%、范围 50%–300%。

**生成帧率**：本机 RTX 4060 上 MuseTalk 约 45–55 ms 一帧（GPU 空闲时），所以 20 fps 刚好是
实时、没有余量，25 和 30 fps 比实时还慢，OBS 自己的编码器还要分走一部分 GPU。默认 15 fps，
选项里没有 30（旧场景里存的 30 会按 25 用并在日志里提示）。worker 追不上时，插件只保留最近 1 秒的
音频、更早的丢掉，并在日志里报 `the worker is not keeping up with real time` —— 嘴会滞后、掉帧，
但 OBS 不会被拖住。

**自动降帧**：10 秒内被迫丢掉的音频超过 25% 时，插件通过 `SET_FPS` 消息让 worker 立刻降一档
（25→20→15，最低 15），不需要重启、不需要重新加载模型，日志里会写
`the worker cannot keep up at N fps ... generating at M fps instead`。这只在本次运行内生效，
属性里存的值不变；想一开始就用合适的值，直接选 15。

**GPU 利用率**：worker 用的是 CUDA（日志第一行 `loading models on cuda:0`）。任务管理器「性能 → GPU」
默认画的是 **3D** 引擎，CUDA 计算在下拉框里的 **Cuda / Compute_0**，所以会看上去几乎为 0；
`nvidia-smi` 更直接：worker 工作时本机实测利用率 30–55%、功耗 62–69 W（空闲 13 W）、显存 3.5 GB。
8 GB 显卡上**只能同时有一份 MuseTalk**：两份加起来加上 OBS 就把显存占满，实测会触发
`CUDA error: an illegal memory access`。worker 现在遇到未处理的异常会立即 `os._exit(1)`，
不再停在驱动清理里占着管道和显存；插件看到它退出后会按退避重拉。

**嘴形为什么看上去"假"，以及怎么处理的**（都在 `musetalk_engine.py` / `avatar-engine-sidecar.c`）：

嘴形本身不是电平触发的，是 Whisper 对语音内容的特征驱动的。流式处理带来的两个人为痕迹是：

1. **窗口边界的周期性跳变。** MuseTalk 的音频接口是按"一段音频"设计的，流式只能切成窗口。
   Whisper 编码器用绝对位置编码，同一个声音落在窗口里不同位置，特征就不同，窗口内逐渐漂移、
   下一个窗口又从头开始，嘴形就按窗口周期抖一下。实测窗口交界处的帧间变化是内部的 2.4 倍
   （整段一次处理是 1.09，即没有）。给窗口两侧加上下文**没有用**（试了 0.2–0.8 秒，仍是 1.7–2.1
   倍），因为这不是缺上下文。现在每个窗口 0.75 秒，两侧各带 0.3 秒上下文只取中间，并且新窗口开头
   3 帧用"上一窗口对这几帧的估计"平滑过渡到"本窗口的估计"（上一窗口的右侧上下文本来就算过这几帧），
   交界处降到 1.08–1.11，和整段一次处理的 1.09 一致，且不增加 UNet 开销。
2. **成串到达、只显示最新一帧。** worker 一批 8 帧同时到，渲染只显示最新的那帧，嘴形就变成每半秒
   更新一次的阶梯。现在帧先进队列，按生成帧率逐帧播放；队列积压超过 1.5 秒（卡顿刚恢复）才跳过旧帧。

**嘴形是不是"跟着内容"**：是。MuseTalk 吃的是 Whisper 对语音声学内容的特征，不需要文字，也不需要字幕。
在一段真实的中文讲解音频上量化（嘴部变化量 vs 响度，帧时间戳在音频时间线上）：相关系数 0.70–0.85，
最佳偏移几乎为 0，也就是模型本身是对齐的。看上去"无关"主要有两个来源：

1. **延迟**：画面比声音晚 1.5–2.5 秒（见下）。连续讲话时嘴的动作和此刻听到的内容对不上，就像不相干、停不下来。
2. **停顿时嘴还在动**：模型在停顿（呼吸、底噪、上一个词的尾音）里仍有接近说话时一半的动作幅度，
   「口型幅度」放大把它一起放大了。现在放大按语音能量门控：说话时全幅，停顿时降到模型原偏移的
   0.4 倍（门限 -52…-40 dBFS，释放 60 dB/s，不让词内的轻辅音把嘴合上）。同一段音频上，
   停顿时的残余动作 5.4 → 1.5（停顿/说话之比 0.48 → 0.17），与响度的相关系数 0.70 → 0.85。
   试过更低的门限（-58…-46、-62…-50）：停顿更不安静（2.6、4.2），说话时开口略大，取舍后保留 -52…-40。

**眨眼**（属性里的「眨眼」，默认开）：生成的画面只有下半张脸，眼睛永远是照片里睁着的样子，一眨不眨本身就是
最先让人觉得假的地方。worker 在准备头像时用 MuseTalk 自带的 dwpose 人脸关键点（68 点里每只眼 6 个点）
拟合出上、下眼睑两条抛物线，经 `EYES` 消息发给插件（10 个 float32 一只眼）；插件在 GPU 上画眨眼：
把眼睛上方一小块皮肤整块"盖"下来，边缘沿眼睑曲线从睁开位置落到下眼睑，再加一条睫毛线。
这样做而不是拉伸眼睛本身的像素，因为拉伸在眼睑要盖住整只眼时会出现竖条纹（原型里试过）。
时机比画法更要紧：眨眼不能按固定节奏，所以间隔在 2–6 秒之间随机（实测 10 分钟约 170 次、平均 3.5 秒），
约 15% 的眨眼后面紧跟一下，闭 80 ms、睁 140 ms。没找到人脸（动物/卡通）、worker 没连上时不眨。
`avatar-blink-test`（要 GPU，在 `bin/64bit` 下手动跑）把着色器渲染到离屏纹理写出 BMP，与 numpy 原型逐像素对比
（眼部平均差 1.8–2.4，同一幅图 b=0 时和原照片的基线差是 1.2）；`avatar-blink-timing-test` 不需要 GPU，
验证次数、间隔、时长、闭睁速度。

**延迟与音画同步**：嘴形比声音晚，约等于窗口 0.75 秒 + 右侧上下文 0.3 秒 + 推理时间 + 一帧插值，
实测 1.7–2.5 秒（15 fps）。OBS 日志里的 `frame lag` 就是当前**实际显示**的画面比声音晚多少毫秒
（由引擎报告它画了哪一帧）。

**自动让声音等嘴**（属性里的「让声音等嘴」，默认开）：插件每秒测一次这个延迟，攒够 15 秒稳定样本后，
把驱动音频源的 OBS **同步偏移**设成这个值（四舍五入到 50 ms，变化超过 150 ms 才再调，避免反复咔哒）。
这样成立的原因在 `libobs/obs-source.c` 的 `source_output_audio_data`：对异步音频源，同步偏移只推迟混音里的
声音，而口型的音频抽取回调拿到的是**未偏移**的原始数据，所以推迟混音不会连口型的输入一起推迟。
这是本插件唯一会改别的源的设置：改之前的原值记在内存里，也记在头像源自己的设置里
（`_sync_restore_source` / `_sync_restore_ms`），OBS 重启后能接着管；关掉这个选项、换音频源、删除头像源时
还原；你在「高级音频属性」里手动改过偏移，它就不再管。

MuseTalk 必须用它自己 venv 里的解释器 —— torch、CUDA 都装在那里，系统 Python 没有。

worker 的 stdout/stderr 写到 OBS 日志旁边的 `logs/avatar-worker.log`（便携模式下是
`config/obs-studio/logs/`）。解释器找不到、import 失败这类问题发生在握手之前，只有这个文件
能看到。每次启动前会写一行 `---- launching worker ----` 和完整命令行；OBS 本身的日志里也会
记 `started the worker (pid …)`、`worker exited with code …` 和下一次重拉的间隔。

配置的路径不存在时，插件在日志里报错并退回手动模式，而不是反复重拉一个注定起不来的命令。

### 手动启动

取消「自动启动 worker」后，插件只创建管道并等待，管道名打在 OBS 日志里（也显示在属性页）：

```
[obs-avatar sidecar: '头像直播'] waiting for a worker on \\.\pipe\ppobs-avatar-1234-000001ab...
```

把那个名字抄给 worker：

```bash
python ppobs_avatar_worker.py --pipe "\\.\pipe\ppobs-avatar-1234-000001ab"
```

好处是 worker 的输出直接在终端里看得见，排查协议问题比翻日志快得多。

检查线格式，不需要管道也不需要 OBS：

```bash
python ppobs_avatar_worker.py --selftest
```

## 两个引擎

| `--engine` | 说明 |
|---|---|
| `auto`（默认） | 有可用的 MuseTalk 就用，否则回落到 stub 并发一条 LOG 说明原因 |
| `stub` | 强制用占位引擎 |
| `musetalk` | 强制用真模型；不可用则报 ERROR 退出，而不是悄悄降级 |

**stub 引擎**不需要任何第三方依赖（纯标准库），画一张占位脸，嘴的开合跟着音频电平走。
它的作用不是好看，而是让整条链路在 3.4GB 权重到位之前就能验证：取音 → 重采样 →
管道 → 帧 → 上屏。盯着那张嘴对自己说话，还能直接看出端到端延迟 —— 那正是阶段 D 要补偿的
那个数。

**MuseTalk 引擎**还没实现。它会在构造时加载准备好的头像包（coords / latents / mask）
以及 whisper-tiny、UNet、VAE decoder，然后每个音频窗跑一次
whisper → UNet → VAE decode → 融合。

## 权重放哪

插件启动时会把资源目录打进日志：

```
[obs-avatar] asset and model directory: ../../config/background-models
```

便携模式下即 `build_x64/rundir/RelWithDebInfo/config/background-models`。MuseTalk 权重放
`background-models/musetalk/`，准备好的头像包放 `background-models/avatars/<id>/`。

## 许可证

并入发行包前必须逐条核验 MuseTalk 依赖权重的商用授权，见
`docs/avatar-lipsync-design.md` §4.3。MuseTalk 自己的代码是 MIT、官方声明权重可商用，但
**SD v1.4 衍生的 UNet** 和**人脸检测／解析权重**这两项还没核验完，后者风险最高（部分
mmpose/dwpose 系权重为非商用）。这是阻断项，不是待办。
